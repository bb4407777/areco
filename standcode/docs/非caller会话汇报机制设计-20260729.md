## 0. 一句话结论

**推荐方案 D：cron 驱动的"收割巡检 harvest01"**——一个不改 areco 服务端、零微信新管路的独立巡检进程，把所有**非 main 通道收件箱条目**和**无 caller 跟踪的房间新结果**统一"拍平"进 main 通道收件箱，复用既有的 `inbox --digest → cc-send` 路径送达高律师微信。候选 B 是它的骨架，C 的"完成标记"和 A 的"实时快通道"作为可选增强层叠加。**不推荐把 A（服务端事件钩子）作为 v1**。

## 1. 问题与现状

### 1.1 汇报缺口（四类"结果烂在房间里"的来源）

只有走 **caller 主动 `dispatch()`** 的任务才有汇报闭环：

```
caller.dispatch → dispatches 面包屑 → poll_result(轮询 tasks.db+红绿灯)
              → _finalize_waiter/write_inbox 落 data/inbox/{task_id}.json
              → process_inbox_callback / inbox --digest → cc-send → 高律师微信
```

**没有 caller 跟踪**的四类活动，结果无法送达：

| 来源 | 例子 | 为什么漏 |
|---|---|---|
| ① room 里直接 @成员 | 高律师/某 stand 在房里 @stand，stand 干完回房 | 无 task_id、无面包屑、无 poll |
| ② secretary-01 分身房间 36a9180a | secretary-01 自己派 Worker/Thinker | 结果落 `data/inbox/` 但 `channel=secretary-01`，**主 digest 跳过**；且分身无 weixin，无法自送微信 |
| ③ stand 之间协作 | A 房内 stand 互相对话产出 | 双方都是 assistant 消息，无人轮询 |
| ④ areco-msg 手动投递 | 终端 `areco-msg.mjs room-x Stand 任务` | fire-and-forget 直写 SQLite，无 caller 收件 |

### 1.2 现状调研三条铁律（决定方案形状）

**铁律 1：areco 服务端没有任何对外事件出口。**
- 无 webhook / SSE / 长连接 / room 维度的 EventEmitter / pub-sub。
- 唯一推送是 WebSocket `gateway.broadcast`，**只面向 web 浏览器前端**，无外部订阅者。
- `lastMessageAt` 不是持久化字段，是 `GET /api/rooms` 时 `SELECT team, MAX(created_at) FROM messages GROUP BY team` 的**只读投影**。
- 服务端唯一"感知消息"的方式 = 自己 1s `tick()` 轮询 `tasks.db`；外部 agent 唯一"感知消息"的方式 = 也去轮询 `tasks.db`（caller 就这么干，0.5s）。
- 证据：`packages/server/src/services/room-relay.ts`（`onMessageStored` 私有方法 :294 是最接近的统一收敛点，但无订阅注册；`captureTick` :748 自动捕获 agent 回复）、`packages/server/src/ws/gateway.ts:414`（broadcast 仅 ws.send）。

**铁律 2：`data/inbox/` 已是送达微信的万能汇。**
- 收件箱按 `task_id` 命名（`{task_id}.json/.processing/.done`），只有 caller 的 waiter 写它。
- `channel` 字段做通道隔离：`~/.qclaw-hermes`→`main`、`profiles/secretary-01`→`secretary-01`；`inbox --digest` 默认只取本通道。
- 送达微信走 `process_inbox_callback`/`inbox --digest` → `cc-send`（`CC_SEND_BIN`，caller.py:4371）。
- **关键**：`~/.standcode/tasks/` 与 `standcode/data/inbox/` 是**所有 Hermes 实例共享**的（secretary-01 无独立 `.standcode` home）。所以 secretary-01 的结果**确实在共享收件箱里**，只是被 `channel=secretary-01` 挡在主 digest 之外——这是缺口②的根因，也是最便宜的修复点。

**铁律 3：Hermes 唤醒契约明确，但不应作主路径。**
- 程序化唤醒主 Hermes：`POST http://127.0.0.1:8642/v1/chat/completions`，`Authorization: Bearer hermes-local-key`，`{"model":"k3","messages":[...]}`，触发**完整 Agent 循环**（带工具/技能/terminal），0 冷启。
- secretary-01 同形契约在 :8646。**secretary-01 无 weixin 平台**（headless，只有 api_server）。
- `max_concurrent_runs=10`，超出返 429 + Retry-After——**唤醒会和服务中的微信会话抢额度**。
- **caller.py 不唤醒 Hermes**：方向相反，是 Hermes 用 terminal 跑 caller.py；caller 只跟 areco(8790)+tasks.db 说话，结果经 cc-send 回微信。
- 因此"通知主 Hermes"≠ 必须 POST 唤醒；更稳的是**把结果塞进收件箱让既有 digest 拉取**（拉模式，gateway 宕了也不丢）。

## 2. 候选方案对比（五维评估）

| 维度 | A. 服务端事件钩子→POST 唤醒 | B. cron 轮询→汇总唤醒 | C. 约定汇报房→secretary 转达 | **D. 收割巡检 harvest01（推荐）** |
|---|---|---|---|---|
| **实时性** | ★★★★★ ~1s（跟服务端 tick） | ★★ 5–10min（可调） | ★★★ 取决于 secretary 读房节奏 | ★★ 骨架同 B；**紧急房可加 1min 快扫** |
| **实现成本** | ★★ 改 OSS areco 服务端 TS + 出站 HTTP + 防轰炸去抖 + durable outbox | ★★★★★ 独立脚本，零服务端改动，复用 caller 直读 SQLite | ★★★ infra 低，但**约定纪律成本高** + 教 secretary 汇总行为 | ★★★★ 独立脚本复用 caller 大量现成函数 |
| **消息轰炸** | ★ 高风险，每条 assistant 消息都 POST，须重做 settle 去抖 | ★★★★★ 天然批次，易加 quiet-hours/限频 | ★★★ 靠 secretary 聚合，需智能批 | ★★★★★ settle 门控 + 批次聚合 |
| **与 inbox 兼容** | ★★ 旁路另起通道，绕开 task_id/channel | ★★★★★ 可直接写 inbox 复用 digest→cc-send | ★★★ secretary 转 main = POST 8642，可写 inbox | ★★★★★ **直接复用 inbox/digest/cc-send，零新微信管路** |
| **断线恢复** | ★ fire-and-forget，POST 失败即丢，须自建 outbox | ★★★★★ HW 水位线幂等，重启即追平（同 reconcile） | ★ 源端 push，**源不可靠正是现在漏的原因**，漏报即丢 | ★★★★★ HW 水位线 + 收件箱 `.done` 幂等 |

### 为什么不选 A 作 v1
- 要改 **OSS areco 服务端**（Apache-2.0），把一个私有 Hermes 端点硬编码进开源项目是设计坏味——要做也该是**通用 webhook 特性**，那是更大的工程。
- 事件 fire-and-forget，POST 失败（Hermes 宕/429）即丢，断线恢复要自建 durable outbox，复杂度陡增。
- 轰炸风险最高：每条 assistant 消息都触发，必须把 caller 已有的 settle 去抖逻辑在服务端**再实现一遍**。
- **A 的正确归宿**：等 areco 真的长出通用事件总线后，让 harvest01 改成"订阅事件"而非"轮询"——是演进终点，不是 v1。

### 为什么不选 C
- 缺口**本身**就是因为这些会话 ad-hoc、不守 caller 约定；C 要求它们守一条**新**约定（干完去固定房 @secretary），会以同样的方式失败。
- 但 C 有一个好零件：stand 最清楚自己"干完了什么"。把这个抽成**轻量完成标记**（`✅HARVEST: <一句话>`），让 harvest01 优先采信它作摘要——C 降级为 D 的**保真增强层**，不作感知机制。

## 3. 推荐方案 D：收割巡检 harvest01（详细设计）

**一句话**：cron 调度的独立巡检，做两件事，把一切非 main 视野的结果"拍平"进 main 收件箱 digest。

### 3.1 两个 Job

**Job 1｜通道交叉中继（cross-relay）—— 专治缺口②**
- 扫 `standcode/data/inbox/*.json`（pending），凡 `channel != "main"`（如 `secretary-01`）的条目：把 `result_text`/`request_summary` 重写为一条 **main 通道**的 `harvest-*` 条目（`channel:"main"`, `source:"harvest"`, 加来源标注"via <原 channel>"），原条目改 `.done`（幂等，防下次重复）。
- 因 secretary-01 **无 weixin**，这是它的结果送达高律师的**唯一**路径——不是重复，是补缺。
- 极低成本：纯文件读写，复用 `read_inbox`/`write_inbox`/`_inbox_path`（caller.py:4238/4246/4257）。

**Job 2｜房间收割（room harvest）—— 专治缺口①③④**
- 读 `~/.standcode/tasks/*.json` 的 `dispatches` 面包屑 → 得到**当前有 caller 跟踪**的 room_id 集合（排除这些，避免与 caller 重复）。
- 列房（`GET /api/rooms` 或读 `rooms.json`），对每个**未跟踪**的房：
  - 读 `messages` 表该房自 HW 水位线后的消息（复用 `get_messages` caller.py:1769 的直读 SQLite 模式）。
  - 筛 **assistant 消息**：`from_agent != humanName` 且成员 `kind=='session'`（人类转述 `human_relay=1` 不算）。
  - **settle 门控**（防轰炸核心）：仅当该房 trafficLight 到 `conclusion/idle/exited`，**或**最后一条 assistant 消息后静默 ≥60s，才收割——把一整轮对话**捆成一条**报告，而非逐条。
  - 收割：合成 `data/inbox/harvest-{room}-{ts}.json`（`result_text` = 新 assistant 消息摘要、`channel:"main"`、`source:"harvest"`），推进 `~/.standcode/harvest/{room}.hw` 水位线。
- 既有 `inbox --digest → cc-send` 自动送达，**微信侧零改动**。

### 3.2 关注域（watch scope）—— 替代 A 的"手工关注列表"

**自动计算**，无需维护：所有房 − 当前 caller 跟踪的房。天然覆盖①③④。secretary-01 的房（36a9180a）在 Job 1 已通过收件箱覆盖；若它有**不经收件箱**的房内对话，由 Job 2 兜底（在 `harvest.json` 显式 include）。

`~/.standcode/harvest.json`（小配置）：`include_rooms`（显式纳入，如 secretary 房）、`denylist`（噪音房）、`quiet_hours`（免打扰时段不送微信）、`per_room_min_interval`（同房最低报告间隔，如 10min）。

### 3.3 断线恢复（与 reconcile 同构）
- 每房 HW 水位线文件 `~/.standcode/harvest/{room}.hw`（存 `message_id` + `created_at` 复合键防 id 复用）。
- 巡检进程死了/机器重启 → 下一次 cron 从水位线追平所有漏掉的消息，幂等不重不漏。
- 与既有 `reconcile`（专救"死 waiter"）**互补**：reconcile 救有面包屑但 waiter 死了的；harvest 救**从无面包屑**的。死 waiter 的房在 reconcile 接手前若超时，harvest 也会兜底（排除逻辑只排"活"跟踪）。

### 3.4 节奏与落点
- cron `harvest01` 注册进 **`/Users/gao/.cc-connect/crons/jobs.json`**（与 `reconcile`:270、`zhigan01`:348 同款机制，**不引系统 crontab**——守章程）。
- 默认 5–10min；紧急房可另设 1min 快扫（独立 cron 条目，仅扫 `include_rooms`，省量）。

3. **【实现】Job 1 交叉中继**：扫 `standcode/data/inbox/*.json`，`channel!='main'` 的重写为 main harvest 条目、原条目 `.done`。

### Phase 2｜可选：实时快通道（仅紧急房需要实时时）
8. **二选一**：
   - **8a（推荐，零 OSS 耦合）**：harvest 对 `include_rooms` 跑 1min 独立 cron 快扫——近实时而不改 areco。
   - **8b（演进）**：areco 服务端加**通用** webhook（`room-relay.ts:onMessageStored` :294 注入，按房订阅，per-room 去抖，durable outbox 表防丢，尊重 429/Retry-After）；harvest 订阅之，替轮询。**禁止**把 Hermes 端点硬编码进服务端。
9. **【实现】快通道唤醒**：紧急房 settle 后 `POST :8642/v1/chat/completions` 一句"X 房完成：<摘要>"，带 Retry-After 退避；**默认关**，避免抢微信额度。

### Phase 3｜可选：完成标记保真层（C 的好零件）
10. **【约定】** 在注入 note 模板（`room-relay.ts:448`）/ StandCode 系统 prompt 里，让 stand 干完**非 caller 触发**的活时多发一行 `✅HARVEST: <一句话摘要>`。harvest 优先采信此行作 `result_text`，无则回退 trafficLight settle。

## 5. 风险点与缓解

| 风险 | 缓解 |
|---|---|
| **消息轰炸微信** | settle 门控（conclusion/idle 或 60s 静默才捆报）+ quiet_hours + per_room_min_interval + digest 批聚合；快通道默认关 |
| **secretary-01 结果双送** | 它无 weixin，main harvest 是**唯一**送达路径，非重复；用 `harvest-*` 伪 task_id + `source:harvest` 标记去重；其他通道靠 channel 隔离防窜 |
| **api_server 429 抢额度** | 默认走 inbox（拉模式，零并发压力）；唤醒仅紧急房、尊重 Retry-After |
| **Hermes gateway 宕** | inbox/digest 是拉模式，gateway 挂了结果也不丢，恢复后照送 |
| **"什么算结果"误判** | 复用 caller 成熟的 trafficLight settle（conclusion/idle/exited）；Phase 3 标记层提升保真 |
| **水位线漂移** | id+created_at 复合键；reconcile 同模式已验证 |
| **误排活跟踪房 / 漏排死 waiter** | 只排 `status=='running'`；死 waiter 由 reconcile 接手，harvest 兜底，互补不冲突 |
| **areco OSS 耦合（若上 8b）** | 必须通用 webhook + feature flag，禁 Hermes 硬编码 |
