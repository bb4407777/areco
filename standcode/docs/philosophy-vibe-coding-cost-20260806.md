## 0. 一句话

AI 写代码让你"一直有成就感"，恰恰是最大的陷阱：
你做得出东西，但看不懂流程、不懂运行原理——**能做出 ≠ 能评估**。
Vibe Coding 拓宽了做软件的入口，但没有同等分配评估它的能力。

## 1. 原文核心论点（提炼）

### 1.1 Vibe Coding 对普通人的四个价值（上限就这些）

1. 自动化重复的事
2. 日常工作加速
3. 好看的 demo 验证想法
4. 功能简单、流程清晰的 APP/程序

**仅此而已。** 生产级、数据密集、安全关键的活，vibe 证据最弱。

### 1.2 三份文献支撑（原文引用的 arXiv）

| 文献 | 结论 |
|---|---|
| arXiv 2607.21652（47 来源综述） | 45% 来源报告短期生产力/原型速度提升；**可维护性和长期质量证据「仍然有限」**；证据最强=原型/界面，最弱=生产/数据密集/安全关键 |
| arXiv 2606.23130（真实 vibe-coded 应用扫描） | 漏洞模式与传统开发不同：**占位逻辑被当实现留在线上**（`// TODO` 上了生产）、输入不过滤、密钥直接暴露；根因 = **agent 丢记忆、只顾局部最优**；模型变强能降低发生率但消除不了 |
| arXiv 2605.24521（162 人调查） | 非程序员/新手/专业开发者三组对「AI 代码不可靠」的认知几乎一样；**差的是评估、调试、验证的能力**——入口拓宽了，评估能力没跟上 |

### 1.3 作者结论

- AI 会一直给你成就感，但你不会想更深入——对系统了解越来越模糊
- 把 vibe 用好需要基本功：**写作能力（逻辑思维）+ CS 知识（编程知识）**，有了才能判断 AI 写得对不对
- 好奇心：想知道它为什么能跑、框架是什么、报错是什么意思——这才叫喜欢编程

## 3. 设计启示（给 StandCode 的落地建议）

1. **验收不能靠 agent 自评**：vibe 的教训在 agent 协作里同样成立——worker 自报"完成"不可信，
   必须有外部验收（gate_result / court-doc-verify / father 抽查）
2. **father 就是"对抗一直有成就感"的机制**：单 agent 会一直觉得自己做对了，
   father 的存在让"成就感"过一道外部质检
3. **丢记忆是根因 → 强化 memory 中台**：文章说 agent 丢记忆是漏洞根因，
   StandCode 的 memory.db + skill 沉淀正是对冲手段
4. **占位逻辑检查**：验证门应该包含"输出里有没有残留 TODO/占位符"这类模式检查
5. **AI 写的不对要能判断**：这条对人类和系统都适用——court-docx 六项硬上限、
   court-doc-verify.py 就是"判断能力"的机器化
